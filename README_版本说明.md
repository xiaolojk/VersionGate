## 旧版本（VersionGate v1.x）到底做了什么？

旧版的原理非常简单：**只改协议号**。

基岩版服务端绑定一个协议号（本机是 `2225`），客户端上报的协议号不一致就被挡在门外。旧版插件在网络层拦截登录握手包，把客户端上报的 4 字节协议号改写为服务器协议号，让版本校验通过——**相当于只把"门牌号"改了**。

### 它解决了什么
- ✅ 让 1.26.x 各小版本客户端能"连进来"、进服通报真实版本
- ✅ 精确协议号白名单，不会误伤 1.21.x 等跨代版本

### 它做不到什么（关键局限）

**只改协议号 ≠ 真正兼容。** 协议号只是握手时的版本号字段，而游戏过程中客户端和服务器之间传输的**数据包结构**是由版本决定的。旧版客户端按旧结构发包，新版服务器按新结构解析，两边对不上，就会出现：

- 玩家/实体显示异常、皮肤错乱
- 部分物品、方块、村民交易行为异常
- 某些功能（如新特性、动画、音效）失效或报错
- 严重时可能导致客户端崩溃或掉线

打个比方：旧版只是把信封上的**收件人邮编**改对了，让信能寄到；但信里写的**内容格式**对方根本看不懂。能进门，但没法正常交流。

这就是之前那句质疑——"你就单改了个协议号吗？那有什么用呢？跨版本麻烦的问题就是版本之间的数据包不一样"——说中的要害。**是的，旧版确实只改了协议号，数据包不兼容的问题它没有解决。**

## 新版本（v2.0.0 ProtocolBridge）做了什么？

v2.0 解决的是**真正的难题**：把旧版客户端的游戏包按字段翻译给新版服务器，反向也翻译。

- 基于 Endstone 官方维护的 [`bedrock-protocol`](https://github.com/EndstoneMC/bedrock-protocol) 库，按协议版本对数据包做 `decode` / `encode`
- 翻译流程：旧版 payload → 用旧协议解码成对象 → 逐字段复制到新版对象 → 用新协议编码 → 交给服务器（服务器看到的就是标准新版包）
- 针对 1.26.x 相邻档位实测：2193→2225 共 231 个共有包中，**223 个（96.5%）字节级兼容，只有 7~8 个包需要翻译**，单次翻译约 13µs

它不是"改门牌号"，而是**把信里的内容也翻译成了对方看得懂的语言**。

### v2.0 的三个保护机制
1. **自适应明文检测**：运行时自检 payload 能否被官方库解析；若是密文或不支持的协议，自动进入被动模式，只记录不改写，绝不搞崩服务器
2. **只翻译旧版玩家**：只对其协议号 ≠ 服务器协议号的玩家翻译；同版本玩家零开销
3. **失败放行**：任何翻译异常都吞掉并原样放行，绝不阻断连接

## 我应该下载哪个？

- **想让旧版 1.26.x 客户端真正能玩**：下载 **v2.0.0**，并把 v1.3 的协议号改写功能配合它一起用（v1.3 负责让你连进来，v2.0 负责让包对得上）。
- **只是想进服看一眼、不在意功能异常**：旧版 v1.3 仍可用于相邻版本（如 26.50 → 26.65）。
- **跨大版本（如 1.21 → 1.26）**：暂不支持。v2.0 针对 1.26.x 相邻档位设计；跨大版本字段差异过大，需要逐版本翻译链，不在当前可靠范围。

## 诚实说明

- v2.0 的字段翻译在沙箱中做了 9 项测试全过、231 个包的往返验证，但**尚未经过真实旧版客户端的端到端游玩验证**（沙箱无真实客户端）。部署后请打开 `debug = true`，用一个旧版客户端进服观察日志，确认翻译是否触发。
- Bedrock 协议闭源且 Mojang 每次更新都可能改包结构，跨版本兼容需要持续跟进维护。
